This reference describes the supplied Processing Digital Twin. It makes visible where code represents the Pololu 3Pi+ 32U4 with the StampC3, and where it uses deliberately ideal starting assumptions that can be improved with evidence.

i
How to use this page

Trace a quantity from command to representation

Start with the component you are investigating, locate its matching tab in DigitalTwin, and follow its inputs and outputs. The model describes an explicit hypothesis; physical measurements determine whether that hypothesis is useful.

01
Code map · responsibilities

Digital Twin sketch structure

The DigitalTwin folder is a Processing sketch. The top-level tab creates one Simulator; that application owns time, rendering, TCP comparison, and graphing. RobotSimulation_c coordinates robot-only models without attempting to model the wider environment.

02
Runtime · time · coordinate frame

How Processing represents a run

draw() may be called at a variable display rate, but Simulator.updateRobotModel() accumulates elapsed time and advances the controller and robot model in fixed 10 ms steps. This represents the intended fastest StampC3 control/acquisition cadence while keeping rendering separate.

Representation choices

  • World frame: positions are millimetres; +x is forward/right and +y is upward. Processing’s screen coordinates are transformed before drawing.
  • Surface: surface.png, when supplied, represents the test surface at one pixel per millimetre. Otherwise Processing generates an A3-sized circular-line fallback for the demonstration.
  • Robot view: RobotSimulation_c.draw() is a visual marker for the simulated pose and sensor locations, not a geometric replica of the hardware.
  • Time: RobotSimulation_c.getMillis() supplies simulated milliseconds to Controller_c, mirroring the role of Robot_c.getMillis() on the StampC3.
03
RobotSimulation_c · model façade

Robot interface and cached state

RobotSimulation_c deliberately provides the subset of the StampC3 Robot_c interface used by Controller_c. This lets a controller request sensors, encoder data, pose, and motor commands in both settings, while the underlying source of those values is different.

04
Expected development · MotorsModel

Motor command and wheel-speed model

MotorsModel_c contains one MotorModel_c for each wheel. It is an intentionally ideal starting point: requested PWM is limited to −200 to +200, then mapped linearly to a maximum speed of ±0.25 mm/ms.

What is represented, and what is left to improve

  • Represents: separate left/right requested commands, a hard request limit at ±200, and a wheel-speed value used by the odometry update.
  • Does not represent: measured deadband, asymmetric gain, nonlinear response, output saturation beyond that request limit, noise, slew limiting, or first-order lag.
  • Expected development: revise MotorModel_c.setPWM(...) and/or MotorModel_c.update(...) using measurements of the chosen robot.
  • Check: compare a predicted trajectory or encoder change against a fresh physical observation rather than only fitting the measurements used to choose parameters.
05
Expected development · SurfaceSensorModel

Surface-sensor representation

Five SurfaceSensorModel_c objects are placed in the robot frame and transform their local positions into the world frame. Each samples one pixel from the Processing surface image and maps brightness from black to 2000 and white to 400.

InterfaceMeaningPhysical counterpart
SurfaceSensorModel_c(name, radiusMm, angleDegrees)Defines one ideal sensor position in the robot frame.Represents one of the five downward-facing reflectance channels.
sample(image, x, y, theta)Transforms the sensor location, reads image brightness, and returns an ideal value.Represents a reflectance measurement without electronic or optical imperfections.
RobotSurface_c.reading[5]Cached five-channel result delivered to the controller.Parallels the surface-reading array exposed by the StampC3 interface.

Expected development

Improve SurfaceSensorModel_c when your investigation identifies an effect worth representing, such as offset, gain, saturation, nonlinearity, noise, timing response, or cross-talk. Keep the image as a controllable surface description; do not mistake its ideal brightness for a measured physical response.

06
Expected development · OdometryModel

Pose and encoder representation

OdometryModel_c converts left and right wheel travel into pose and encoder counts. It uses a differential-drive update with a shared wheel radius, wheel separation, and encoder resolution supplied when RobotSimulation_c is created.

Expected development

  • Represents: wheel travel, the mean travel distance, heading change from wheel-travel difference, and encoder counts derived from wheel circumference.
  • Assumption: the supplied geometry is ideal. The model does not separately represent left/right radii or separations.
  • Where to revise: use OdometryModel_c.update(...) and its geometry/conversion parameters, with any corresponding changes in RobotSimulation_c.
  • Evidence: use measured straight-line and turning behaviour to determine whether geometry changes improve prediction.

Develop Controller_c when an improved model changes what a useful controller should command, or when you want to test a clear new control hypothesis. Keep controller changes distinct from model changes so that a prediction can be attributed to the appropriate assumption. Several baseline values are intentionally analogous to the physical template; inspect both source files when exact constants matter.

08
TCP comparison · Graphing

Receiving and comparing physical telemetry

In live-comparison mode, Simulator acts as a TCP client to the StampC3 access point. TCPTelemetry_c parses each 14-field CSV record, and Graphing draws simulation and recent physical values together. The orange ghost is a representation of robot-reported odometry, not ground truth.

ComponentRoleData relationship
TCPTelemetry_c.parse(...)Validates and stores timestamp, pose, requested PWM, encoders, five sensor values, and start signal.Matches the CSV field order emitted by the StampC3 template controller.
Simulator.updateTcpConnection()Connects to the default StampC3 access-point address and consumes input lines.Represents a desktop observer; it does not control the physical robot.
updateLiveClock()Advances the received ghost only to the corresponding simulation time.Aligns a simulated run with the received physical timebase after a start-signal transition.
TimeSeriesGraphRetains rolling motor, sensor, and encoder series for drawing.Compares model output against received robot telemetry; it does not measure independently.
