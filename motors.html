Subsystem:
Motors.

The motors subsystem is composed of many parts. There is the motor actuator itself, the electronics driving and providing power, a quadrature rotary encoder for sensing motor rotation, a gear train, and the wheel as effector output interacting with the contact surface. Electrical, mechanical, physical and software effects all contribute to variances between motors and betweeen robots.

In Phase 1 of this course, we are tasked with measuring and developing a description of the motor subsystem performance, called characterisation. Once we understand how the motor subsystem is operating, we can take this information to improve the simulation model in Phase 2.

In these exercises, the code you will write will be very simple: you will need to activate a motor for some time and record some measurements. Some aspects could be automated with iteration (e.g., loops). However, it will be important to think about whether using iteration may also impact the observed motor performance. You will need to design and write different test cases to measure different characteristics. You will need to think carefully about any assumptions.

It might surprise you that, even though we are focusing on motor output, we are still going to use a sensor. The simplest way to determine the speed of the robot might be to set the motor power, allow the robot to travel a known fixed distance, and record the time it takes from beginning to end. We would then divide the distance by the time to work out the velocity, for example, in meters per second. Taking external measurements like this (external to the robot) are perfectly valid, and sometimes essential. However, a robotic system will also have many sensors which can be used to take more internal measurements (internal to the robot), with very good control of time and other aspects. In the following exercises, we will learn to command the motors and to measure their activity via quadrature rotary encoder sensors.

In general, a .h contains the declarations and definitions - you can think of this as the contents page or index of a book. A .cpp file contains the full implementation code - which is much more like the main body of a book.

The above line of code can be read from right-to-left to help us understand what it does and where it is defined in the code. First, setMotorPWM(...) is a function, which we can identify by the parentheses. The name of the function describes setting the pulse width modulation (PWM) for the motors. PWM is the name given to a technique to approximate an analogue output on a digital output pin (i.e., graduated values between on and off). A digital output pin can only output a high (typically 5v or 3.3v, depending on the microcontroller) or low value (0v). If we could only use a digital output, the motors would be powered either fully-on, or off.

To provide continuous command of a motor (varied power levels), PWM very quickly alternates between high and low values in repetition, generating a square waveform on the output pin. To change the approximate voltage on the digital pin, the pulse (high period) is varied with respect to the low period. A long high period generates a higher voltage, whereas a longer low period generates a lower voltage.

Next, within robot.setMotorPWM(...), the dot (.) can be read as "contained within" the preceding object, robot. The dot operator is used to access functions and variables within an object. To learn more about robot, the next step of investigation is to find where robot is declared. You will find the following line of code at the top of the StampC3_Template.ino file:

This line tells us that robot has the datatype Robot_c - robot is the name to access this memory, and Robot_c is the definition of how the memory is structured for the datatype. The _c suffix is a convention adopted throughout the StampC3_Template code, and it can be read to mean that this datatype is a class. In other areas, _t will be used to mean a unique type, and _s to mean a struct data type.

Stripped Gears

Please do not stop the wheel rotation with your finger or by holding the robot still.

The motors of the robot contain a small gear train that is quite fragile. If you stop the rotation of the wheel whilst the motor is powered, the motor will strip the teeth from the gears. This will cause permanent damage to the robot.

It is also possible to cause similar damage by pushing the robot along a surface at high speed.

Using robot.setMotorPWM(...) sets the power to the motors, it does not control the speed. This is immediately clear if you consider that you can offer some light resistance to the wheel rotation with your finger and the wheel slows down. In later exercises, we will characterise the motor by measuring it's speed. Therefore, we need to learn how to detect and measure the wheel speed.

Each motor on the robot is fitted with a quadrature encoder. The encoder has a disc magnet which rotates above a Hall Effect sensor. This means that when the motor shaft rotates an electronic pulse is created that can be counted. More information on how the encoders work can be found in the official documentation. In this course, counting the pulses and determining whether the wheel is rotating forwards or backwards has been implemented for you. The robot will register a change in wheel rotation and either increment or decrement the rotation count.

To read the current encoder count for the motors, we will utilise a helper function within the Robot_c class. In Robot_c, find

getEncoders()

Reviewing the code in this function, we can observe that the function requests a "snapshot". You can find this snapshot (RobotEncoders_t encoders; ) and other snapshot variables declared at the top of the Robot_c class. This snapshot terminology reflects the fact that the encoder values retrieved were correct at the time they were requested, but that they may have since changed. In real terms, if a snapshot of the encoder counts is retrieved, but the robot continues to move, then we expect that the count stored on the robot itself will have continued updating. We will actually use this property to allow the robot to estimate wheel speed.

Two more helper functions, getLeftEncoderCount(), and getRightEncoderCount(), are provided to attempt to reduce potential confusion about which count represents which wheel. Reviewing the function getLeftEncoderCount(), we can observe that it has the return type of int32_t. This means that the function will return a signed integer number value, whose range is represented across 32 bits. In actuality, 1 bit is reserved to represent the sign of the number (-/+) whilst the remaining 31 bits represent the numeric value. Suffice to say, an int32_t can store very large number values.

Counts of rotation produced by the encoder may seem confusing - how does this map to a rotation or distance travelled? The official documentation for the encoders tells us that one whole rotation of the wheel produces 358.3 encoder counts. We can therefore work out either how much rotation occurs for 1 encoder count ( degrees: \(\frac{360}{358.3}\), or radians: \(\frac{2\pi}{358.3}\)), or how much distance would be travelled by the wheel for one encoder count (wheel circumference divided by 358.3).

To estimate a wheel speed, we will apply the simple speed formula:

\(v = d / t\)

where \(v\) is velocity, \(d\) is distance, and \(t\) is time. To use this equation, where therefore need our robot to identify values of \(d\) and \(t\).

For time, we currently understand that the controller update(...) function calls our test function every 10ms. It is important to know that the exact timing is not strict - the function may not be called at exactly 10ms. Furthermore, if a delay() is inserted, the 10ms timing will likely be lost entirely.

Next, we want to know how far the wheel rotated (or travelled along a surface), \(d\), within that same time interval. To do this, we will need to capture the encoder counts before and after the time interval. This is not as complicated as it might seem. We only need to get the most recent value, and remember the previous value.

We know that the controller code is iterative - meaning, it keeps repeating or looping. Therefore, we can actually use the encoder count at time \(t-1\) (last time step) as the reference for the next encoder count at time \(t\) (current time step). Our distance measurement is fundamentally the difference between two encoder counts. The delta symbol, \(\Delta\), is commonly used to mean the difference:

\(\Delta e^{left} = e^{left}_{t-1} - e^{left}_{t} \\ \Delta e^{right} = e^{right}_{t-1} - e^{right}_{t}\)

where \(e^{left}\) and \(e^{right}\) represent the encoder counts for left and right motor respectively. Deadband: find where motion begins

Approx. 2–4 hours

Open in Google Colab

Goal: use the encoder-speed measurement developed in Exercise 2 to determine whether each motor has a low-PWM command region in which no reliable wheel motion can be detected.

Using robot.setMotorPWM(...) will generate a PWM signal for the left and right motors. At small command magnitudes, the available motor torque may be insufficient to overcome static friction in the motor, gearbox, bearings, tyre contact, or other properties of the task environment. Driver electronics, command handling, and the effective PWM duty cycle can also contribute. The resulting low-PWM command region, where changing the value produces no detectable sustained motion, is commonly described as a deadband.

Deciding that motion has begun is not as simple as observing a change of one encoder count. A wheel may twitch and stop, begin moving only after a delay, or rotate so slowly that a short measurement time interval records no count change. Encoder resolution and timing therefore affect what you can detect. Establishing an exact deadband threshold is therefore very difficult.

Deadband is associated with starting from rest. Once the motor and wheel has started moving consistently, it will have overcome static friction and require less power to operate. Therefore, the command that first causes a stationary wheel to turn may be larger than the command required to keep that wheel turning once it is already moving. These are breakaway and continued-motion behaviours. It is for this reason that measuring deadband is not as simple as sweeping a PWM value from 0 to maximum - each PWM value needs testing from a stopped initial state.

It is also important to note that a deadband region may also differ between the left and right motors, and between forward and reverse rotation. Robot support, weight distribution, surface contact, mechanical load, and the time allowed at rest can change the result. In this exercise, you should evaluate both motors independently.

Deadband matters in robot control, and particularly in Digital Twin systems. When deadband exists, a controller that assumes a small non-zero command creates a proportional movement will be wrong. On a real robot, this discontinuity in the relationship between power and motion can create stuttering or the inability to move at low velocity. In simulation, assuming that a deadband does not exist would mean that any controllers developed in simulation are unlikely to perform as expected when transferred to a real robot.

Motor burn out

In this exercise you are guided to run the motors at the upper limits of wheel speed (e.g., fast motors). If you leave a motor operating at the maximum PWM for a long time, it will get hot and eventually burn out - causing permanent damage. Therefore, you should write code to operate the motors at high speed only for short intermittent periods.

In application, you will find that the discovered upper limit of motor PWM values produce robot movement that is too fast to be useful.

When you increase the PWM command to a wheel, you might expect its speed to keep increasing. A real motor system has a finite operating range, so eventually a larger input to the motor may produce little or no repeatable increase in output. There are also other factors that must be considered. An electronic motor can have varied electrical efficiency across it's input range or with respect to the load it experiences (for more insight, review the plots in the official motor datasheet). Saturation describes this loss of output response to further input.

In this exercise, your goal is to determine whether saturation is visible in your measurements and to state the conditions under which you observed it. On a command-versus-speed plot, saturation may appear as a plateau (a flat portion of the plot). The fastest output response of the motor is not by itself evidence of saturation. A supported claim of saturation needs a repeatable flattening across several PWM command levels.

Observing a plateau in output does not necessarily reveal its cause. Experimentally, we need to construct an argument for the most likely causes. Possible motor-system limits include the motor driver, supply voltage and current, the motor and gearbox, battery condition, and the load at the wheel. Friction, wheel contact, floor surface, and payload can change the response too. These are competing explanations to test. For example, you may discover that the operating surface does or does not have a signficant impact. In these exercises, we can also adopt some sensible assumptions. For example, for this class of robot, we expect it to operate on a level plane. Whether or not your robot will carry extra load (weight) or operate on a smooth surface will be determined by the project context your team has selected for Phase 2 of this course.

This upper limit matters to motion control. If a controller asks an already saturated motor for more output speed, the motor has no further capability in reality and cannot increase. For a two-wheel differential steer robot, if one wheel is not able to respond as expected, the total motion of the robot is likely to behave unexpectedly. Therefore, knowing saturation limits can be accounted for in better control schemes. In the context of this course, we also want to ensure that the Digital Twin simulation is an accurate and useful model of the real robot system. If we do not, any behaviours or parameters determined in simulation are unlikely to have utility in reality.

Gain: measure the response slope

Once the deadband and saturation regions are known, the next question is how strongly the wheel responds within the usable range between them. This response scale is described by the gain. For a motor, gain tells us how much the wheel speed changes for a change in requested PWM. A larger gain means that the same PWM step produces a larger change in wheel speed. In this exercise, we will determine a gain with the assumption that the motor response behaves linearly between input PWM and output wheel speed.

Let \(u\) be requested motor PWM and let \(\hat{\omega}\) be the model's predicted output wheel speed. An ideal proportional model would be:

\[ \hat{\omega}=Gu \]

Here, \(G\) is the gain, a conversion factor whose units depend on how command and wheel speed are represented. For example, if the \(u\) was measured in encoder counts per second, then a value \(G=4\) would predict that increasing \(u\) by 25 PWM changes the output wheel speed by \(4\times25=100\) encoder counts per second.

We know from previous exercises that the motors exhibit a deadband. That means that the output response of the motor will not pass through the origin on a plot. A more useful model is therefore the equation of a straight line:

\[ \hat{\omega}=Gu+c \]

We can interpret this equation in the context of our robotic application: \(G\) represents the slope of the motor response, whilst \(c\) adjusts for the point at which a given PWM coincides with no motor output speed. In this exercise we will experimentally determine a value for \(G\) and \(c\). It is important to recognise that any variation in the task or environment will effect the response of the motor. It is therefore more correct to refer to \(G\) as an operational gain (correct within specific operational constraints). The gain we will determine is not intrinsic to the motor.

During this exercise, you may notice that your motor response is non-linear. Exercise 6 investigates non-linearity specifically. Even if a response can be seed to be non-linear, applying a linear model to a smaller region can still be useful. Sometimes, non-linearity sits outside of the useful range of a response, and so the impact is not as significant. Non-linearity

Approx. 2–4 hours

Open in Google Colab

Goal: determine whether the straight-line gain model developed in Exercise 5 is adequate across the usable motor range, and whether either of two simple non-linear models makes better predictions for commands that were not used to fit any model.

Exercise 5 treated gain as a local slope. If the response were linear across the whole usable range, equal increases in requested PWM would produce approximately equal increases in settled encoder speed. A non-linear response has a changing slope: the response may be relatively flat at lower commands and steeper later, or it may rise quickly and then flatten. This is different from saturation, where further command produces little or no additional response at the upper boundary. A curve can contain both a non-linear moving region and a separate saturation plateau.

The residual plot from Exercise 5 provides a useful starting point. Residuals that are small and irregular across the usable range support a straight-line approximation. A repeatable sequence of residuals that begins on one side of zero, crosses it, and then moves to the other side suggests that the line is missing a curved structure. One unusual measurement is not sufficient: changed battery condition, load, wheel contact, settling time, deadband, saturation, or measurement variation can produce a similar visual impression.

We will compare two simple curved candidates with the straight-line model. The first is a power law. Let \(x\) be a normalised requested PWM and let \(\hat{v}\) be the predicted normalised settled speed:

\[ \hat{v}=x^\gamma \]

The exponent \(\gamma\), pronounced “gamma”, controls the curve. When \(\gamma=1\), the power law has a linear shape. When \(\gamma>1\), the predicted response is flatter at lower commands and becomes steeper later. When \(0<\gamma<1\), it rises more sharply at first and then flattens. Figure 4a shows these different shapes. Gamma describes a fitted relationship; it is not evidence that the motor contains a physical component or hidden parameter called gamma.

The second candidate is a second-order polynomial, also called a quadratic model. It extends a straight line by adding a squared-command term:

\[ \begin{aligned} \text{linear:}\quad &\hat{v}=A+Bx\\ \text{quadratic:}\quad &\hat{v}=A+Bx+Cx^2 \end{aligned} \]

In both equations, \(A\) is the intercept and \(B\) describes the linear trend. The additional coefficient \(C\) allows the quadratic slope to change with command: its sign determines the direction of curvature and its magnitude controls how strongly the curve bends. A complete quadratic graph is a parabola, but the usable motor range may show only a gentle segment of that shape. The equation is therefore a flexible candidate description, not a claim that one quadratic physical mechanism causes the response.

Normalisation places command and speed on comparable scales before fitting the power law. Let \(u_{\min}\) and \(u_{\max}\) be the lower and upper boundaries of the usable command range established from your deadband and saturation evidence. Let \(\omega_{\min}\) and \(\omega_{\max}\) be the corresponding operational settled-speed reference values. Create derived columns:

\[ x=\frac{u-u_{\min}}{u_{\max}-u_{\min}}, \qquad v=\frac{\omega-\omega_{\min}} {\omega_{\max}-\omega_{\min}} \]

Within the stated boundaries, \(x\) and \(v\) are intended to run approximately from 0 to 1. Keep the requested PWM \(u\) and measured encoder speed \(\omega\) unchanged in the raw dataset and add \(x\) and \(v\) only for analysis. Normalisation changes the numerical scale; it does not calibrate PWM into voltage, current, torque, or mechanical power, and it does not remove uncertainty in the estimated boundaries.

Compare the linear, quadratic, and power-law candidates using exactly the same fitting observations and the same held-back commands. For observation \(k\), calculate the normalised residual \(e_k=v_k-\hat{v}_k\). You can summarise prediction error using mean absolute error:

\[ e_k=v_k-\hat{v}_k, \qquad \operatorname{MAE} =\frac{1}{N}\sum_{k=1}^{N}|v_k-\hat{v}_k| \]

Figure 4b illustrates this comparison. The residual patterns reveal structure hidden by the overlaid curves, while the shaded held-back commands test prediction rather than fit. A quadratic has more adjustable coefficients than the power law and can often follow fitting data more closely. That extra flexibility is useful only if it gives repeatably better predictions; otherwise it may be fitting measurement variation. Prefer the simplest model that predicts adequately over the range needed by your digital twin.

Analyse one wheel and direction first, then repeat the same comparison for the other cases. A defensible conclusion may retain the straight line, support one curved candidate only over a stated range, require different models by wheel or direction, or reject all three candidates.

Slew-rate and lag

Open in Google Colab

Exercises 5 and 6 used requested PWM to predict a settled wheel speed. That static relationship identifies the destination of a change, but not how the wheel gets there. When a command changes, motor current, the rotor, gearbox, wheel, robot body, and any embedded processing all take time to respond. A digital twin that jumps immediately to the new settled speed may therefore predict the final motion correctly while predicting the path, stopping distance, or controller timing poorly.

A useful experiment is a step test: hold one command until the wheel speed is steady, change the command once, then retain the complete time series until the new speed settles. Let \(\omega_0\) be the initial speed and let \(\omega_\infty\) be the final settled speed predicted by the static model. Several simple temporal models could connect these two values; they are candidate descriptions to test, not mechanisms to assume.

In a slew-rate model, wheel speed cannot change faster than a limiting rate \(S\):

\(|d\hat{\omega}/dt|\) ≤ \(S\)

Here, \(\hat{\omega}\) is predicted encoder speed and \(S\) has units of encoder-speed change per second, such as counts s−2. A sufficiently large command step then produces an approximately straight ramp whose slope is bounded by \(S\). The same limit need not describe rising and falling responses, both wheels, or both directions.

A different candidate is a first-order lag. Its rate of change is proportional to the remaining distance from the final speed:

\(\tau\,d\hat{\omega}/dt\) = \(\omega_\infty-\hat{\omega}\)
\(\hat{\omega}(t)\) = \(\omega_0+(\omega_\infty-\omega_0)(1-e^{-(t-t_0)/\tau})\)

The time constant \(\tau\) sets the response timescale. For a pure first-order step, the prediction has completed about 63.2% of its total change at \(t=t_0+\tau\). This shortcut is not a general definition of motor response time: it is only a valid estimate of \(\tau\) when a first-order model is adequate and a slew limit is not controlling the early response.

Figure 5a shows why a single rise-time value is not enough. A slew-limited response has an approximately constant slope while the limit is active. A first-order response changes fastest initially, then its slope decreases as it approaches \(\omega_\infty\). A combined model may begin with pronounced curvature and take longer to settle. At a slow sampling or reporting rate these shapes can look deceptively similar, so the evidence must include timestamps and more than a few points across the transient.

The measured trace also includes the measurement pipeline. The supplied controller requests a new cached encoder snapshot on a nominal 10 ms update cycle, whereas publishTelemetry(...) emits records on a separate nominal 50 ms cycle. Wheel speed is itself calculated from a count difference over a time interval. That interval, irregular execution timing, delayed records, or additional averaging can smooth a sharp change. Record the actual elapsed time for every successful snapshot, and distinguish acquisition, speed calculation, and reporting before interpreting a curve as motor physics.

Compare every candidate against the same observations. Fit parameters using one or more repeated steps, plot residuals against elapsed time, and look for structure rather than relying on a fit score alone. Then freeze the parameters and predict a new transition—for example, a different step size or a falling step. Figure 5b illustrates this logic with synthetic data. It does not show the response students should expect: its purpose is to demonstrate how a model that follows one trace can still fail on a genuinely new transition.

Choose steps inside the moving, unsaturated range established earlier, so deadband and saturation do not dominate the transient. Begin and end each trial with a long enough hold to estimate \(\omega_0\) and \(\omega_\infty\), repeat selected trials, and preserve wheel, direction, command, timestamps, counts, calculated speed, and trial identity. A clear slew limit, a clear first-order lag, a combination, or no resolvable delay at the available sampling rate are all legitimate evidence-led outcomes. State the tested range and resolution rather than converting an unresolved effect into a fitted certainty.

Investigation brief

  1. Choose a useful command step. Begin with the deadband, saturation, gain, and response-shape evidence from Exercises 3–6. For one wheel and one direction, choose an initial PWM and a final PWM that both lie comfortably inside the moving, unsaturated range. The change should be large enough to produce a measurable transient, but it does not need to approach the limits of the motor.
    1. Write down the instantaneous, slew-only, and first-order candidates that you will compare. Treat a combined slew-and-lag model as an additional candidate to use only if the simpler models leave clear evidence unexplained.
    2. Choose in advance which repeated transitions will be used for fitting and which different transition will be held back for prediction. A falling step or a new step size can provide a useful held-back test.
    3. Record why the selected commands avoid the deadband and saturation regions. This helps separate dynamic behaviour from the static limits investigated earlier.
  2. Prepare a separate step-response test. Keep the functions developed in the earlier exercises and create testStepResponse(Robot_c &robot, unsigned long now). Call only testStepResponse(robot, now) from update(...) while collecting this dataset. Use a test phase and TaskTimer_c to implement the sequence without blocking:
    1. hold the initial command until the speed is steady;
    2. apply the final command once and mark the step time;
    3. continue collecting encoder snapshots while the speed changes;
    4. hold the final command long enough to estimate the settled speed; and
    5. stop the motor safely before ending or repeating the trial.
    Keep command generation separate from telemetry reporting so that printing or transmitting a record cannot alter the intended step timing.

  3. Check the sequence safely before a full trial. First run the function with the robot upside down. Confirm that the initial command, single step, final hold, and stop occur in the intended order. Check that every reported row identifies the trial, wheel, direction, requested PWM, timestamp, and encoder count. It is also useful to report the current test phase so that you can locate the command change when analysing the data.
  4. Pilot the measurement timing. Preserve the actual timestamp and encoder count at every accepted snapshot, then calculate speed using the measured elapsed interval. Do not assume that a nominal 10 ms task period means that every observation is exactly 10 ms apart. Check separately how often encoder snapshots are acquired, wheel speed is calculated, and records are reported.
    1. Plot the command and the unaveraged speed from one pilot trial against time.
    2. Count how many observations occur while the speed is changing. If there are only one or two, the available timing may not distinguish an instantaneous response from a short lag or slew-limited ramp.
    3. Avoid adding smoothing simply to make the curve look cleaner. Smoothing can hide the early response that this exercise is intended to investigate.
  5. Collect repeated transitions. Begin with a moderate rising step and repeat it under comparable conditions. Keep the surface, wheel loading, battery condition, initial hold, final hold, and sampling procedure as consistent as practical. Then collect the different step chosen for held-back prediction, such as another step size or a falling step, if it is safe to do so. Retain every raw record and label each trial rather than saving only an average response.
  6. Prepare the time-series data for comparison. Preserve the original timestamps, encoder counts, commands, and trial labels. Add derived columns for elapsed time from the command step and calculated wheel speed. For each trial, estimate \(\omega_0\) from the initial hold and \(\omega_\infty\) from the final hold, recording the interval and observations used for each estimate.
    1. Plot individual repeated trials before calculating any average so that differences in timing and response remain visible.
    2. Check that the initial and final holds are long enough to support stable estimates. If they are not, revise the trial timing and collect the measurement again.
    3. Keep unusual observations and inspect their timestamps and trial conditions before deciding whether they represent measurement variation, a reporting problem, or repeatable behaviour.
  7. Fit the candidate models fairly. Fit the instantaneous, slew-only, and first-order candidates using the same named fitting trials and compare their predictions over the complete transient. Add the combined model only if the residuals from the simpler candidates show a repeatable structure that the extra parameter could reasonably address. Record the fitted slew rate, time constant, and any other applicable parameters with units and uncertainty or sensitivity estimates.
    1. Plot every candidate against the same measured trace and calculate residuals in the original speed units at the same timestamps.
    2. Look for residual patterns over time. For example, a model may predict the early response poorly even if it reaches the correct final speed.
    3. Use the same error summary for every candidate and compare its size with variation between repeated trials. A more complicated model is useful only if its improvement is meaningful at the resolution of the experiment.
    4. Use the 63.2% shortcut to estimate \(\tau\) only when the trace is consistent with a first-order response and the early change is not controlled by a slew limit.
  8. Test a complete held-back transition. Freeze the fitted parameters before examining the reserved trial. Use each candidate to predict the full response to the new step, then compare prediction and observation at the recorded timestamps. Plot the held-back residuals and report their size in the original speed units. A different step size or a falling step is a stronger test of the model than withholding a few samples from the same fitted trace.
  9. Investigate how widely the result applies. Once the method works for one wheel and direction, consider repeating it for the other wheel, the opposite direction, or a different part of the usable command range. Use the same procedure, but allow the fitted parameters to differ. Decide whether a shared dynamic model predicts these cases adequately or whether separate parameters provide a worthwhile improvement for your digital twin.
  10. State what the experiment can resolve. Your evidence should include the raw timestamped records, tested commands and conditions, acquisition and reporting intervals, repeated trials, model equations, fitted parameters with units, uncertainty, residual plots, and held-back prediction errors. Conclude whether the observations support slew limiting, first-order lag, a combination, another explanation, or no resolvable delay at the available sampling rate. State the wheel, direction, command range, surface, load, and timing resolution to which the conclusion applies.
Expected outcome: a timestamped dynamic response

You should finish with a reproducible step-test dataset and a model comparison that distinguishes what happened immediately after a command change from the settled response measured earlier. A justified detection limit or rejection of all proposed models is a valid result.

AI-assisted investigation brief

Use AI as a timing reviewer and a tutor for dynamic models. A rounded speed trace could reflect the motor response, the measurement process, or both. AI has not observed the robot, so you will need to make those possibilities distinguishable through recorded commands, counts and times.

Your first milestone is a pilot trace with enough timing information to decide whether the transition can be resolved, not a fitted time constant. Choose whether AI would be most useful for the logger, a worked model update or a comparison plot. Provide only the relevant source or notebook cell, labelled data excerpt and the question it should answer. If it cannot read your plot, describe the axes and provide the values behind the feature. Ask what was actually inspected or executed before relying on its account.

  1. Predict three possible responses. Choose a step between two moving, unsaturated commands using your earlier evidence. Sketch an instantaneous change, a rate-limited ramp and a first-order approach to the final speed. Explain what observations could separate them. Choose repeated fitting transitions and reserve a complete different step size or falling transition before fitting anything.
  2. Trace three clocks. Draw when commands change, encoders are acquired, and measurements are reported. Give AI the relevant Controller.cpp, Robot.cpp and TaskTimer source excerpts and ask it to verify each arrow by file and symbol. Retain the nominal 10 ms acquisition cycle; the separate telemetry period is not the sampling interval. Explain how a speed calculated over a count window averages motion within that window.
  3. Review a bounded state machine. Write pseudocode for initial hold, one marked command step, final hold and stop, then ask AI to inspect one transition at a time. Use persistent state and timers without blocking. Preserve button start, explicit completion and abort stops, and one active motor-command routine. Compile and pilot with wheels clear, cables away and short moderate commands within ±200 PWM. Do not restrain a powered wheel.

  3. Predict an entire new transition. Freeze dynamic parameters before evaluating the reserved trial. State how its starting and final speeds are obtained. If you first measure where this new trial settles, you can ask whether the model describes how it gets there; that is a conditional test of transient shape, not a prediction of its endpoint. Compare all candidates at the same timestamps, using residuals in the same speed units, and explain how count-window averaging was treated.
