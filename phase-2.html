Simulation orientation · controller contract

Explore the Simulation and Its Controller

40–60 min

Following the previous exercise, you should be able to run the Processing based simulation. Before connecting it to your robot, let's get comfortable with what it represents and how its parts work together. The moving robot on screen is being operated by some code called a controller, just as your physical robot has been. However, with the robot we compile the code and upload it to the real robot. For the simulation counterpart, all code remains within the Processing environment. The simulation counterpart of the real robot also provides interfaces to read simulated sensors and operate simulated motors. The simulated robots measurements and motion, come from simple models provided in the Processing code. In the group work section of this course, you will want to review the simulation in comparison to your real robot, and begin to decide which parts may need updating.

By exploring the code in the Processing simulation provided to you, you will notice that a class named Controller_c exists again, just like the StampC3_Template code used as a starting point with the real robot. The duplication of the Controller_c class is an intentional design choice. In the simplest terms, the intention is that, by doing your code development within the Controller_c class, you should be able to move code you have developed between the robot and the Processing simulation with only very minor modifications.

Whilst the Processing environment and Arduino environment do appear very similar, there are important differences. Fundamentally, Processing and Arduino require code in different languages. Arduino expects C/C++, whilst Processing is based in Java. Both languages have a C-style of syntax, such as the use of semi-colons to terminate a line of code, and curly-braces for code encapsulation. Other important differences emerge from each platforms intended use or target. For example, Arduino has built in functions such as Serial.println(...), which is designed to interface to a common Serial interface across Arduino microcontrollers. Processing does not have Serial as a common interface, it is not designed to program microcontrollers, so Serial.println(...) does not exist as a built in function. If you copy your controller code from Arduino to Processing, you will likely get some errors such as Processing not recognising Serial.println(...). Likewise, if you develop Controller_c code in Processing that uses more advanced Java features, such as ArrayList, you will not be able to immediately transfer your Processing Controller_c to Arduino, compile and upload without errors.

When you want to move your developed code from Arduino (the robot) to the Processing simulation, you will want to move only the additional code you have authored. For example, if you attempt to copy the entire Controller.cpp file from Arduino into Processing, Processing will generate an error against the Serial.printf(...) command within the Controller_c::publishTelemetry(...) function (see here).

We can consider the Controller_c class framework and Robot_c class as a type of contract of use for both systems. Whilst the Robot_c class attempts to provide a common interface to the robot, you will need to exercise some decision making and discretion when developing code across both the real robot and the simulation. Our aim is to generally follow a measurement–decision–command pattern of code in each, and to identify what must be adapted when transferring a controller. As you make progress, you will want to explore further into the simulated models of the motors and sensors, and then selectively develop each to better align the operation of both the real robot and the simulated robot.

Robot behaviour · finite-state machines

Build a Finite-State Machine

60–90 min

In this exercise we build a new finite state machine (FSM) to operate the real robot through different behaviours. Our overall objective is to get the robot to explore within the large black rectangle, avoiding the black line of the rectangle when necessary. A finite state machine (FSM) describes a system using a limited set of states, each representing a distinct mode of operation. The system occupies one state at a time and changes state when a specified event or condition occurs. Its current state determines how it responds and what actions it performs. Organising your code by an FSM is particularly useful because entire behaviours can be added, removed, enable/disabled, or organised into more complicated chains of behaviours.

The line following behaviour provided to you in the example StampC3_Template code already has an operating finite state machine. Reviewing the function runLineFollower(...) (see here), we can observe that the variable mode is evaluated across different if-statements to determine different robot behaviours. The following states are defined in Controller.h (see here): 


    enum Mode {
      WAITING,
      FOLLOWING_LINE,
      SEARCHING_FOR_LINE,
      STOPPED
    };

The above block of code is an enumeration, it used to associate human-readable words to numeric values. WAITING, FOLLOWING_LINE, SEARCHING_FOR_LINE, STOPPED are the enumerators, creating named constant values. By default, C++ assigns these values integers beginning with 0 (WAITING = 0, FOLLOWING_LINE = 1, etc). We can therefore think of the variable mode within runLineFollower(...) as operating like a flag to signal the current operational state of the robot. FSMs typically do two things: first, ascertain what the current state is, and whether it is still true; second, execute some code for a current state. If mode == SEARCHING_FOR_LINE, the controlling code can decide whether the state needs to change based on any new information available to the robot. Reviewing runLineFollower(...) further, we can see an example of this occuring: 


  if (mode == SEARCHING_FOR_LINE) {
    if (line_detected) {
      mode = FOLLOWING_LINE;
    } else if (now - recovery_start_ms >= RECOVERY_TIMEOUT_MS) {
      mode = STOPPED;
    }
  }

In the above, we can see how a FSM can transition from one state to another, based on the information available. First, the current state is ascertained with if( mode == SEARCHING_FOR_LINE ). We can think of this as the robot asking itself "what am I doing right now?". If the robot is searching for a line, the FSM has 3 possible decisions.

  1. if( line_detected ): If a line is detected, then the robot should transition to the state FOLLOWING_LINE. This is achieved by simply changing the value of mode. Subsequent code will then operate based on the surface sensor readings to configure the motors.
  2. else if( now - recovery_start_ms >= RECOVERY_TIMEOUT_MS ): This condition is checking whether the robot has been searching for a line for a period longer than or equal to RECOVERY_TIMEOUT_MS. If true, the FSM transitions to a STOPPED state. Setting mode to STOPPED will mean subsequent code will disable the PWM sent to the motors.
  3. Implicitly, if neither of the above 2 transitions occur, then the robot will simply remain in the SEARCHING_FOR_LINE state.

In the next section of code of runLineFollower(...), we see that the FSM then executes code encapsulated by some state flags. In the 3 lines of code, line following is produced as an implicit behaviour, if the neither of the two prior state flags were true: 


  if (mode == STOPPED) {
    robot.setMotorPWM(0, 0);
    return;
  }

  if (mode == SEARCHING_FOR_LINE) {
    robot.setMotorPWM(RECOVERY_LEFT_PWM, RECOVERY_RIGHT_PWM);
    return;
  }

  float error = (float)robot.surface.reading[1] - (float)robot.surface.reading[3];
  float turn = error * LINE_FOLLOW_GAIN;
  robot.setMotorPWM(BASE_PWM - turn, BASE_PWM + turn);

In the middle of the diagram, we can trace two states and two state transitions which form a loop - the robot will follow a line, and if it loses the line, search to find the line again:

If the robot encounters the black boundary it move to reliably turn away. We will also build in an end state, stopping the robot after a period of time has elapsed.

You already have a useful starting point: Controller_c stores the modes used by the supplied line follower. We will keep our new FSM inside this class too, so its state, timing and decisions stay together. Robot_c will continue to provide the functions for reading the robot and requesting motor commands. If classes still feel unfamiliar, that is fine: the steps below show where each declaration and function belongs. Our first exploring behaviour will simply drive forwards while no black line is detected. On detecting the boundary, the robot will reverse briefly, turn, and try exploring again. Therefore, the avoidance behaviour has two parts - reversing and turning. To achieve reverse and turn, we will implement these as time limited operations. Therefore, once the sensors detect a black boundary, the robot will reverse for a short period of time. A separate timer will end the whole trial, including any avoidance in progress. For example, by modifying any timing values, or later updating timed-motion for better motion control techniques.       case State::WAITING:

          } else {
            enterState(State::EXPLORING, now);
          }
        }
        break;

      case State::FINISHED:
        // Remain here until the controller is reset.
        break;

      robot.setMotorPWM(-30, -30);

      robot.setMotorPWM(-30, 30);

    case State::WAITING:
    case State::FINISHED:

      break;
  }
}

Real Robot: Compensate for Motor Deadband

60–90 min

In Phase 1, your motor deadband investigation examined the range of PWM commands that fail to reliably produce sustained wheel rotation. Your repeated measurements should indicate an interval where starting becomes reliable for each tested wheel and direction. This estimate will be different for each robot and the conditions you measured it under.

In this exercise, we will develop code that avoids setting motor PWM values on the robot in the measured deadband region. This is called deadband compensation. We can imagine making a bridge across the low-PWM region when sending a movement request to the motor. The deadband region still exists physically on the motor, but we attempt to map a command signal across it.

In previous exercises we have written code to operate the motors by working with the PWM value directly. In this exercise we will adopt a normalised command signal, \(q\). The deadband compensation will map \(q\) to a PWM value. We will expect \(q\) to be normalised to the range \([-1 : +1]\), where negative values represent the motor moving in reverse.

Considering only the forward direction of rotation for the motor intiailly, we can imagine that \(q = 0\) should produce no motor output (no PWM), whilst \(q = 1\) would represents a request for the upper-limit of motor PWM value. For the intermediate range, we need to provide an equation to map \(q\) across the operable PWM range of the motor. In effect, any value that is non-zero should begin at the PWM identified as the boundary of the deadband region.

From your deadband investigation, we can use \(b\) to represent the identified boundary of the deadband, and \(U\) as the upper-limit of PWM value, and imagine a function \(u(q)\) that returns a compensated PWM value:

\[u(q)=\begin{cases}0,&q=0\\b+(U-b)q,&0<q\leq1.\end{cases}\]

We can read the above equation to understand that when the provided \(q\) command value is zero, the PWM output provided is 0. When \(q\) is provided as positive and non-zero, a mapping occurs between \(q\) and the output PWM. We can read \( (U-q)\) as the range of operable PWM values (non-deadband region), which is scaled by \(q\). Finally, the scaled value is offset by \(b\), so that the output PWM will start from the deadband region boundary. This current mapping will only work as intended for positive non-zero values of \(q\).

For example, let \(b=20\), \(U=144\), and a decreasing value of \(q\):

\[u(0.1)=20+(144-20)\times0.1=32.4 \\ u(0.01)=20+(144-20)\times0.01=21.24 \\ u(0.001)=20+(144-20)\times0.001=20.124\]

In the above, as \(q\) approaches zero, the compensated PWM approaches the value of \(b\). At exactly zero, it will return zero. At exactly 1, it will return \(U\). Although the normalised request \(q\) can vary continuously, the PWM deliberately jumps between a zero value (no output) to an offset value starting at the identified PWM value that produces wheel rotation.

To map continuously from positive values of \(q\) to negative values of \(q\), we will need to catch the sign of \(q\) and amend the mapping equation to produce negative PWM values. This can be reviewed in the exercise steps below.

This deadband compensation may be useful when writing controllers for later robot behaviours. Howwever, this compensation technique does not guarantee a smooth increase in wheel speed from rest. Physical effects such as friction may mean that the motor output will jump from no motion to sudden motion. The following exercise steps will test whether starting becomes more reliable and what limits remain at low speeds.

In the simulation counterpart, it will be important to consider whether to model the deadband region or not. This should be informed by how well a deadband compensation bridges the deadband region in reality. If your robot still produces a sudden transition in wheel speed with the deadband compensation, it will be more appropriate to model both the deadband region and the deadband compensation within the simulation.

float Controller_c::compensateDeadband(float q) {
  if( q == 0.0 ) return 0.0;

  // Catch invalid values.
  q = constrain( q, -1.0, 1.0 );

  float pwm = 0.0;

  if( q < 0.0 ) {
    pwm = db_reverse + ( (pwm_limit - db_reverse) * abs(q) );
    pwm *= -1.0; 
  } else {
    pwm = db_forward + ( (pwm_limit - db_forward) * q );
  }

  return pwm;

}

Simulation: Model the Surface Reflectance Sensor's Spatial Footprint

40–60 min

In this exercise we will use the measurements taken in Phase 1 of the spatial footprint of the surface reflecance sensor to improve the simulation model. The DigitalTwin simulation provided to you has a very simply model of the surface reflectance sensors. The simulation currently calculates which pixel is beneath the simulated sensor and returns the brightness value for that pixel. The simulation models 1 pixel as a 1x1mm square. Therefore, the simulation currently represents a surface reflectance sensor as measuring a single 1x1mm point. In reality, the real robot surface reflectance sensor will sample a surface area. Because the real sensor receives light from an area, neighbouring parts of the surface can contribute to the overall reading.

The previous exercise (Exercise 9) explored how to transform a single pixel brightness to better represent the real robot sensor response (e.g., offset, saturation, non-linearity). In this exercise we will focus on using multiple pixels to contribute to the sensors brightness reading in the simulator. You will need to combine this exercise with the previous exercise to implement both a spatial footprint and the transformation from pixel brightness to better match the real sensor response.

To simulate a spatial footprint we will start with a 3 × 3 square of pixels. The initial approach will take the centre pixel and its eight neighbours all weighted equally (all contributing equally to an average brightness). This exercise will then extend the approach by adjusting the weighting to simulate a more circular sampling of the surface.

Going further: circular and weighted footprints

In the previous exercise step, the square model makes two assumptions: every pixel inside a square contributes, and each contributes equally. By assigning a weight to each pixel, we can effectively change the shape of the sampled area. The following two example functions have been written to scale well when footprintHalfWidthPixels is changed, and so they avoid hard-coded constant values (e.g., a set of specific weights). Add the following functions inside SurfaceSensorModel_c, beside squareFootprintBrightnessAtPixel(...). Keep the previous square function so that you can compare the alternatives.

  1. Sample a circular area. Include a pixel only when its offset lies within a chosen radius: 
    float circularFootprintBrightnessAtPixel(PImage image, int pixelX, int pixelY) {
  int radius = footprintHalfWidthPixels;
  float total = 0;
  int count = 0;

  for (int dy = -radius; dy <= radius; dy++) {
    for (int dx = -radius; dx <= radius; dx++) {

      // To include this pixel or not?
      if (dx * dx + dy * dy <= radius * radius) {
        total += pointBrightnessAtPixel(image, pixelX + dx, pixelY + dy);
        count++;
      }
    }
  }
  return total / count;
}

    The condition uses the squared distance from the centre, avoiding a square-root calculation. Only included pixels increase count, so we divide by the number actually sampled. The existing point helper still handles samples outside the image.

    With footprintHalfWidthPixels = 1, this includes the centre and its four immediate neighbours, leaving out the square's corners. At this resolution the circle is a five-pixel cross; radius 2 includes 13 pixels and gives a less coarse approximation. Radius 0 retains the centre pixel. This model assumes equal sensitivity inside its boundary and none beyond it.

  2. Give central pixels more influence. A sensor may respond more strongly to the surface directly beneath it than to the edges of its footprint. A weighted average lets us represent that possibility. For example, a 3 × 3 square could use these relative weights: 
    1  2  1
2  4  2
1  2  1

    The centre contributes four times as much as a corner. Each pixel is multipled by the weight value, which are then summed, and then divided by the sum of the weights. In this example, the sum of the weights would be 16. Note that, using a weight of 0 would remove a pixel. The following function generates the example 3x3 weights when the half-width is 1, and extends the same pattern to larger squares:

    float weightedFootprintBrightnessAtPixel(PImage image, int pixelX, int pixelY) {
  int radius = footprintHalfWidthPixels;
  float total = 0;
  float totalWeight = 0;

  for (int dy = -radius; dy <= radius; dy++) {
    for (int dx = -radius; dx <= radius; dx++) {
      float weightX = radius + 1 - abs(dx);
      float weightY = radius + 1 - abs(dy);
      float weight = weightX * weightY;
      total += weight * pointBrightnessAtPixel(image, pixelX + dx, pixelY + dy);
      totalWeight += weight;
    }
  }
  return total / totalWeight;
}

    abs(...) gives the distance from zero along each axis. The weight decreases as that distance increases. Dividing by totalWeight, rather than the pixel count, preserves the brightness of a uniform surface. Setting a half-width of 0 again samples only the centre pixel.

Simulation: Update the Simulated Motor Speed Response

90–120 min + extensions

The Digital Twin simulation provided to you uses a linear mapping between PWM to the robot motion. The linear mapping assumes an input PWM range between -200 and +200, and maps this to a maximum wheel velocity of +/-0.25mm/ms (millimeter per millisecond). From your Phase 1 investigation of the motors subsystem, you will be able to identify whether or not this is accurate. This provided linear mapping assumes that doubling PWM doubles wheel speed, and that any non-zero command produces motion. In Phase 1, deadband, gain and response-shape measurements guide you to test those assumptions.

A forward motor model predicts speed from the command sent to the motor, rather than measuring the output speed. Our simulation model will be feedforward - for a given PWM command, what wheel speed should the simulated wheel have? However, this process can quickly get complicated. For example, if you have followed Phase 2 Exercise 8 Compensate for Deadband, you real robot may now effectively "skip over" a region of PWM commands - should the real robot response be modelled in simulation, before a simulation of deadband compensation? In this exercise, we will assume that deadband compensation (or other mitigations) have not been applied - so we will work from your Phase 1 measurements of the real robot only.

We will begin with one motor in its positive-PWM direction. A simple model predicts zero speed in a measured no-motion PWM region (deadband region) and uses a fitted straight line (linear fit) over an interval of PWM that produces motion. Importantly, the transition from deadband to motion is not necessarily gradual - the linear fit does not necessarily cross the x-axis at the boundary of the deadband. For example, when sufficient PWM is provided to cause wheel rotation, the wheel may jump to a wheel speed rather than gradually increase in wheel speed.

When transferring the work you have done from Phase 1, you will also need to ensure that the implementation in simulation will have right units. The Phase 1 plots use encoder counts per second, whilst the provided simulation advances wheel travel in millimetres per millisecond. Matching the overall response but confusing units would give the robot the wrong motion. This exercise does not explore acceleration, stopping time or the effect of changing load.

Simulation: Model the Motor's Response Over Time

In Exercise 11, we changed the relationship between PWM and wheel speed. However, the simulated wheel still reaches the calculated speed immediately. On the real robot, you have likely observed that a wheel may take time to accelerate and may continue turning after a zero command. These transitions affect the distance travelled, even when the final speed is correct.

To improve the simulation model, we will create two representations of speed. We will separate the target speed, calculated from PWM, from the current speed, stored from the previous simulation step. A simple first-order lag will adjust the current speed towards the target by closing a fraction of the remaining difference each step. The change is initially fast, then becomes smaller as the wheel approaches its target.

The model's time constant controls how quickly this happens. After one time constant, about 63% of the initial speed difference has closed. We will implement this response using an illustrative time constant of 200 ms. Choosing a value from your real robot's measurements and evaluating the model are areas for further work.

Going further: implement a wheel-speed slew-rate limit

In the previous steps we implemented a first-order lag. A lag creates a speed change fastest when the target is far away from the current speed. A slew-rate limit instead allows only a fixed maximum change per unit time, regardless of any difference between current and target speeds. In effect, this produces a straight ramp until the target is reached. The two can be combined, but they will interact. For example, if a slew-rate is set to a high value, we may see the rate of change decrease as the current speed approaches the target - so the result is not always a constant rate of change. A slew-rate can also be used without a lag.

To implement a slew-rate, we will start by adding a class variable. Update the global scope are of MotorModel_c to look like the following:

  float speedMmPerMs = 0;

  float speedChangePerMs = 0.0005;

  float maximumChange = speedChangePerMs * dtMs;
  float change = constrain(targetSpeed - speedMmPerMs, -maximumChange, maximumChange);
  return speedMmPerMs + change;
}

The above function is intended to limit how much a speed can be changed (slew-rate, or rate-limiting). Therefore, the function is constraining acceleration and/or decelaration applied to a velocity. The rate is in mm per ms per ms (\(mm/ms^2\)). With this example setting, a 10 ms step permits a speed change of at most 0.005 mm/ms in either direction. The function constrain(...) limits the maximum rate of change, but will leave smaller rates of change at their present value. You can set a positive rate for each motor separately.

  //return targetSpeed;
}

At this point, we will have implemented both a first-order lag per motor, and slew-rate. Importantly, the slew-rate model assumes that the rate limiting is the same for acceleration and deceleration. However, in reality, acceleration and deceleration may have different dynamics. For example, acceleration is actuated by the robot (given power) and must overcome resistance (friction, etc.). In comparison, during deceleration the same resistance will help slow the wheel.

Simulation: Model Robot Motion from Wheel Geometry

60–90 min + extensions

The provided DigitalTwin simulation currently models the simulated robots motion directly from wheel speed quantities. The wheel speed quantities are mapped directly from commanded PWM values given to the simulated robot. Therefore, the simulation currently by-passes any effects of the geometry of the robot.

From your Phase 1 investigation of the odometry subsystem, you should be familiar with the idea that two parameters in particular influence the estimated pose of the robot: the wheel radius and the wheel separation.

The simpler case to understand is the wheel radius. The encoder counts provide an indication of how much a wheel has rotated, where the Pololu 3Pi+ robot produces 358.3 counts per full revolution. However, the rotation needs to be translated to a distance travelled by the wheel, which is determined by the wheel radius (e.g., the distance travelled by a wheel is a proportion of the wheel circumference, \(c = 2 \pi r\)).

Imagine two wheels making the same number of revolutions, but one wheel has a slightly larger radius. The larger wheel travels further with each revolution. On a differential-drive robot, this difference in travel makes the robot follow a curve. The distance between the wheels also matters: a wider separation produces a smaller heading change for the same difference in wheel travel.

The supplied DigitalTwin maps PWM directly to wheel speed in mm/ms. It uses that speed to calculate travel, so changing a wheel radius does not change the simulated robot's motion. In this exercise, we will make the quantity of wheel rotation explicit, then use separate left and right wheel radii to calculate travel. By doing this, we should be able to set a different wheel radius for each wheel, and observe a resultant curved motion. With different wheel radii, even if the wheels rotate by the same number of encoder counts, they will have travelled different distances.
