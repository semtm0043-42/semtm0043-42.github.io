Simulation orientation · controller contract

Explore the Simulation and Its Controller

40–60 min

Following the previous exercise, you should be able to run the Processing based simulation. Before connecting it to your robot, let's get comfortable with what it represents and how its parts work together. The moving robot on screen is being operated by some code called a controller, just as your physical robot has been. However, with the robot we compile the code and upload it to the real robot. For the simulation counterpart, all code remains within the Processing environment. The simulation counterpart of the real robot also provides interfaces to read simulated sensors and operate simulated motors. The simulated robots measurements and motion, come from simple models provided in the Processing code. In the group work section of this course, you will want to review the simulation in comparison to your real robot, and begin to decide which parts may need updating.

By exploring the code in the Processing simulation provided to you, you will notice that a class named Controller_c exists again, just like the StampC3_Template code used as a starting point with the real robot. The duplication of the Controller_c class is an intentional design choice. In the simplest terms, the intention is that, by doing your code development within the Controller_c class, you should be able to move code you have developed between the robot and the Processing simulation with only very minor modifications.

Whilst the Processing environment and Arduino environment do appear very similar, there are important differences. Fundamentally, Processing and Arduino require code in different languages. Arduino expects C/C++, whilst Processing is based in Java. Both languages have a C-style of syntax, such as the use of semi-colons to terminate a line of code, and curly-braces for code encapsulation. Other important differences emerge from each platforms intended use or target. For example, Arduino has built in functions such as Serial.println(...), which is designed to interface to a common Serial interface across Arduino microcontrollers. Processing does not have Serial as a common interface, it is not designed to program microcontrollers, so Serial.println(...) does not exist as a built in function. If you copy your controller code from Arduino to Processing, you will likely get some errors such as Processing not recognising Serial.println(...). Likewise, if you develop Controller_c code in Processing that uses more advanced Java features, such as ArrayList, you will not be able to immediately transfer your Processing Controller_c to Arduino, compile and upload without errors.

When you want to move your developed code from Arduino (the robot) to the Processing simulation, you will want to move only the additional code you have authored. For example, if you attempt to copy the entire Controller.cpp file from Arduino into Processing, Processing will generate an error against the Serial.printf(...) command within the Controller_c::publishTelemetry(...) function (see here).

The Processing code is missing the if( robot.isButtonPressed() ) block because the simulation does not include a button model. Another difference is that the StampC3_Template version includes the line of code odometry.update(...), which is supports the odometry subsystem investigation specific to the real robot (i.e., not relevant to the simulation). We can also observe that the arguments provided to the update(...) function call differ slightly - the StampC3_Template version expects both Robot_c &robot, RobotWifiAP &server, whilst DigitalTwin only expects Robot_c robot. The server interface only exists on the real robot StampC3 because it is hosting a Wi-Fi network which your computer connects to, this does not have a simulated counterpart.

It is also important to notice that for reading the sensors and commanding the motors, both code extracts are accessing the robot interfance, for example, robot.setMotorPWM(...), robot.getEncoders() and robot.getSurfaceSensors(). In this way, the robot class (Robot.cpp/.h in StampC3_Template Arduino code, and RobotSimulation.pde in the DigitalTwin Processing code) provides a common interface, or Application Programmer Interface (API) to interchangably operate either the real robot or the simulated robot.

We can consider the Controller_c class framework and Robot_c class as a type of contract of use for both systems. Whilst the Robot_c class attempts to provide a common interface to the robot, you will need to exercise some decision making and discretion when developing code across both the real robot and the simulation. Our aim is to generally follow a measurement–decision–command pattern of code in each, and to identify what must be adapted when transferring a controller. As you make progress, you will want to explore further into the simulated models of the motors and sensors, and then selectively develop each to better align the operation of both the real robot and the simulated robot.

If you have made extensive use of Serial.print() in Arduino, this can be substituted in Processing with just print() and println() (i.e., removing the Serial prefix). In processing, print() and println() produce output in the lower black console of the main editor window.

Robot behaviour · finite-state machines

Build a Finite-State Machine

60–90 min

In this exercise we build a new finite state machine (FSM) to operate the real robot through different behaviours. Our overall objective is to get the robot to explore within the large black rectangle, avoiding the black line of the rectangle when necessary. A finite state machine (FSM) describes a system using a limited set of states, each representing a distinct mode of operation. The system occupies one state at a time and changes state when a specified event or condition occurs. Its current state determines how it responds and what actions it performs. Organising your code by an FSM is particularly useful because entire behaviours can be added, removed, enable/disabled, or organised into more complicated chains of behaviours.

The line following behaviour provided to you in the example StampC3_Template code already has an operating finite state machine. Reviewing the function runLineFollower(...) (see here), we can observe that the variable mode is evaluated across different if-statements to determine different robot behaviours. The following states are defined in Controller.h (see here): 


    enum Mode {
      WAITING,
      FOLLOWING_LINE,
      SEARCHING_FOR_LINE,
      STOPPED
    };

The above block of code is an enumeration, it used to associate human-readable words to numeric values. WAITING, FOLLOWING_LINE, SEARCHING_FOR_LINE, STOPPED are the enumerators, creating named constant values. By default, C++ assigns these values integers beginning with 0 (WAITING = 0, FOLLOWING_LINE = 1, etc). We can therefore think of the variable mode within runLineFollower(...) as operating like a flag to signal the current operational state of the robot. FSMs typically do two things: first, ascertain what the current state is, and whether it is still true; second, execute some code for a current state. If mode == SEARCHING_FOR_LINE, the controlling code can decide whether the state needs to change based on any new information available to the robot. Reviewing runLineFollower(...) further, we can see an example of this occuring: 


  if (mode == SEARCHING_FOR_LINE) {
    if (line_detected) {
      mode = FOLLOWING_LINE;
    } else if (now - recovery_start_ms >= RECOVERY_TIMEOUT_MS) {
      mode = STOPPED;
    }
  }

In the above, we can see how a FSM can transition from one state to another, based on the information available. First, the current state is ascertained with if( mode == SEARCHING_FOR_LINE ). We can think of this as the robot asking itself "what am I doing right now?". If the robot is searching for a line, the FSM has 3 possible decisions.

  1. if( line_detected ): If a line is detected, then the robot should transition to the state FOLLOWING_LINE. This is achieved by simply changing the value of mode. Subsequent code will then operate based on the surface sensor readings to configure the motors.
  2. else if( now - recovery_start_ms >= RECOVERY_TIMEOUT_MS ): This condition is checking whether the robot has been searching for a line for a period longer than or equal to RECOVERY_TIMEOUT_MS. If true, the FSM transitions to a STOPPED state. Setting mode to STOPPED will mean subsequent code will disable the PWM sent to the motors.
  3. Implicitly, if neither of the above 2 transitions occur, then the robot will simply remain in the SEARCHING_FOR_LINE state.

In the next section of code of runLineFollower(...), we see that the FSM then executes code encapsulated by some state flags. In the 3 lines of code, line following is produced as an implicit behaviour, if the neither of the two prior state flags were true: 


  if (mode == STOPPED) {
    robot.setMotorPWM(0, 0);
    return;
  }

  if (mode == SEARCHING_FOR_LINE) {
    robot.setMotorPWM(RECOVERY_LEFT_PWM, RECOVERY_RIGHT_PWM);
    return;
  }

  float error = (float)robot.surface.reading[1] - (float)robot.surface.reading[3];
  float turn = error * LINE_FOLLOW_GAIN;
  robot.setMotorPWM(BASE_PWM - turn, BASE_PWM + turn);

Considering the states and transitions, it is possible to create simple FSM diagrams using blocks as states and labelled arrows as transitions. In the middle of the diagram, we can trace two states and two state transitions which form a loop - the robot will follow a line, and if it loses the line, search to find the line again:

In this exercise, we will design a slightly larger FSM with the aim of controlling the robot to move around within the large black rectangle boundary on the A3 test sheet provided to you. If the robot encounters the black boundary it move to reliably turn away. We will also build in an end state, stopping the robot after a period of time has elapsed.

You already have a useful starting point: Controller_c stores the modes used by the supplied line follower. We will keep our new FSM inside this class too, so its state, timing and decisions stay together. Robot_c will continue to provide the functions for reading the robot and requesting motor commands. If classes still feel unfamiliar, that is fine: the steps below show where each declaration and function belongs. It will be useful to review the following state-transition diagram for the exploration and avoidance behaviour:

Our first exploring behaviour will simply drive forwards while no black line is detected. On detecting the boundary, the robot will reverse briefly, turn, and try exploring again. Therefore, the avoidance behaviour has two parts - reversing and turning. To achieve reverse and turn, we will implement these as time limited operations. Therefore, once the sensors detect a black boundary, the robot will reverse for a short period of time. A separate timer will end the whole trial, including any avoidance in progress. You can build and test each part in turn; it does not need to work perfectly on the first attempt.

Once you have the basic exploring and avoidance behaviours working, you are encouraged to explore them further to investigate the overall effects on the robot behaviour. For example, by modifying any timing values, or later updating timed-motion for better motion control techniques. A timed reverse does not guarantee a particular distance, and a timed turn does not guarantee a particular angle. Likewise, this exercise uses fixed threshold values for sensors, and sensor readings can be unreliable. We will start by using your Phase 1 measurements to choose a line-detection threshold.

state_start_ms = 0;

    state_start_ms records when the current behaviour began. trial_start_ms records the button press that starts the whole trial and must not restart during avoidance.     void Controller_c::enterState(State next_state, unsigned long now) {
  state = next_state;
  state_start_ms = now;

  if (Serial) {
    Serial.printf("FSM,%lu,%u\n", now, static_cast<unsigned int>(state));
  }
}

    Controller_c:: identifies this as a function belonging to our controller class. The log records a transition once, when it happens. The state numbers follow the declaration order: 0 is WAITING, 1 is EXPLORING, 2 is REVERSING, 3 is TURNING, and 4 is FINISHED. Initialisation does not print a transition record.

    Only call this function when changing state. Calling it on every update would repeatedly restart the state's clock, so a timed transition might never happen.

  7. Turn sensor readings into a boundary decision. Beneath enterState(...), add the helper function below. This newer function checks all 5 sensors, so that an outer sensor can also trigger avoidance behaviour. 
    bool Controller_c::boundaryDetected(const Robot_c &robot) const {
  for (uint8_t channel = 0; channel < 5; ++channel) {
    if (robot.surface.reading[channel] >= LINE_THRESHOLD) {
      return true;
    }
  }
  return false;
}

    This is our operational definition of “line detected”, not a measurement of the robot's position within the rectangle. Before continuing, explain what the function returns when only one sensor exceeds the threshold, and when none does.

  8. Write the state machine. Beneath boundaryDetected(...), add the function below. The overall deadline is checked first. If time remains, the first switch chooses a transition; the second chooses motor commands for the resulting state. Entering FINISHED therefore requests zero PWM in the same update. The durations and PWM values are starting choices to test using your robot.
    • The following code extract introduces a switch case statement. You can think of a switch case statement as being similar to an if-statement. The switch case statement evaluates its expression and begins executing at the matching case label. For example, case State::WAITING is equivalent to if( state == State::WAITING). In a switch case statement, the break; command it used to ensure that only 1 case block operates - unless it is required for sequential cases to be evaulated in turn. It is possible to configure a switch case statement to execute several cases that evaluate as true by omitting the break command - this is called drop-through or fall-through.
    void Controller_c::runStateMachine(Robot_c &robot, unsigned long now) {
  const unsigned long trial_duration_ms = 20000UL;
  const unsigned long reverse_duration_ms = 350UL;
  const unsigned long turn_duration_ms = 600UL;
  bool line_detected = boundaryDetected(robot);
  bool trial_running = state != State::WAITING && state != State::FINISHED;

  // 1. The trial deadline takes priority over every moving state.
  if (trial_running && now - trial_start_ms >= trial_duration_ms) {
    enterState(State::FINISHED, now);
  } else {
    switch (state) {
      case State::WAITING:
        if (robot.isButtonPressed()) {
          signal = 1;
          trial_start_ms = now;
          enterState(State::EXPLORING, now);
        }
        break;

      case State::EXPLORING:
        if (line_detected) {
          enterState(State::REVERSING, now);
        }
        break;

      case State::REVERSING:
        if (now - state_start_ms >= reverse_duration_ms) {
          enterState(State::TURNING, now);
        }
        break;

      case State::TURNING:
        if (now - state_start_ms >= turn_duration_ms) {
          if (line_detected) {
            enterState(State::REVERSING, now);
          } else {
            enterState(State::EXPLORING, now);
          }
        }
        break;

      case State::FINISHED:
        // Remain here until the controller is reset.
        break;
    }
  }

  // 2. Apply the commands for the resulting state.
  switch (state) {
    case State::EXPLORING:
      robot.setMotorPWM(30, 30);
      break;

    case State::REVERSING:
      robot.setMotorPWM(-30, -30);
      break;

    case State::TURNING:
      robot.setMotorPWM(-30, 30);
      break;

    case State::WAITING:
    case State::FINISHED:
      robot.setMotorPWM(0, 0);
      break;
  }
}

    Each case selects a state; break ends that branch of the switch. During EXPLORING, no detected line means no transition, so forward motion continues. During avoidance, the short state timers let the robot back away and reorient before checking whether to explore again. If the sensors still report a line after turning, it repeats avoidance.

    now - state_start_ms is time in the current state; now - trial_start_ms is time since the trial began. Keeping the timestamps as unsigned long handles timer wraparound for these short intervals. The UL suffix gives each duration the same type. We use >= because updates may skip over the exact target millisecond. Trace a line detection just before the deadline, then a call at the deadline: why must the stop take priority?
