Familiarising with the Odometry Model

Your copy of StampC3_Template contains OdometryModel.cpp/.h, which has the source code for a complete but simple kinematic model using Euler integration. Euler integration approximates continuous-time motion using discrete time steps - we update the model once during each time step. The simple model provided also approximates the continuous motion of the robot using two sequential operations within each update. First, translation - moving the robot forwards or backwards along its current heading. Second, rotation - changing the robot's orientation, which then becomes the heading used for the next update.

When the robot is powered on, its initial position is configured as the origin (\(x = 0, y = 0, \theta=0\)). At heading zero the robot faces along +x. Positive rotation turns towards +y, which we would observe as anticlockwise rotation when viewed from above.

The model has 4 essential parameters: the time step, the wheel radius, the wheel separation, and the number of encoder counts per wheel revolution (CPR). The CPR should be considered as correct and fixed - the manufacturer of the robot specifies this as 358.3 counts per revolution. Your task across the following exercises is to first improve the odometry on board the robot, and then measure and evaluate the overall performance. Your findings will then be carried over into Phase 2, the group project element on the Digital Twin simulation.

Importantly, for our odometric model, we do not want to know the total count of encoder pulses since the robot was powered on. The total count for each motor does not describe the potential complexity of the motion path taken by the robot. For example, some turning movements (rotating on the spot) or reverse manoeuvrers will cause the encoder count to decrease, not just increase. Inspecting only the total count does not represent these motion dynamics. Instead, our odometric model will update in discrete time steps - repeated measurements taken with a spacing of a small interval of time. The odometric model therefore computes the difference between two encoder counts spaced by an interval of time. We can understand this as asking "how far did the wheel travel in this time step?". This allows for a piecewise estimation of how the robot moved to be constructed iteratively.

In these exercises you are guided to develop code for the StampC3 within the Controller_c class (Controller.h file). The Controller_c class framework implements a 10ms interval in the update() function, which in turn called the runLineFollower() example function. This 10ms schedule was created to allow the Pololu 3Pi+ robot sufficient time to execute it's own code to read sensors, control motors, respond to I2C requests, and so on. The Controller_c class is also written to be directly compatible with the Digital Twin simulation code in Processing - which you will work with closely in Phase 2 of this course. Therefore, as much as possible you should preserve the general design of the Controller_c class. That way, you will be able to directly transfer the control code for your robot between the real robot and the simulated robot.

Reading encoders and estimating motion

Approx. 1.5–3 hours

Goal: understand the translation of encoder counts through the odometry class, produce a reusable record of odometry measurements for later use.

Each motor on the robot is fitted with a quadrature encoder. The encoder has a disc magnet which rotates above a Hall Effect sensor. This means that when the motor shaft rotates an electronic pulse is created that can be counted. More information on how the encoders work can be found in the official documentation. In this course, counting the pulses and determining whether the wheel is rotating forwards or backwards has been implemented for you. The robot will register a change in wheel rotation and either increment or decrement the rotation count.

To read the current encoder count for the motors, we will utilise a helper function within the Robot_c class (defined in Robot.h). In Robot.cpp, find getEncoders(). Reviewing the code in this function, we can observe that the function requests a "snapshot". You can find this snapshot (encoders) and other snapshot variables declared at the top of the Robot_c class. This snapshot terminology reflects the fact that the encoder values retrieved were correct at the time they were requested, but that they may have since changed. In real terms, if a snapshot of the encoder counts is retrieved, but the robot continues to move, then we expect that the count stored on the robot itself will have continued updating.

Two more helper functions, getLeftEncoderCount(), and getRightEncoderCount(), are provided to attempt to reduce potential confusion about which count represents which wheel. Reviewing the function getLeftEncoderCount(), we can observe that it has the return type of int32_t. This means that the function will return a signed integer number value, whose range is represented across 32 bits. In actuality, 1 bit is reserved to represent the sign of the number (-/+) whilst the remaining 31 bits represent the numeric value. Suffice to say, an int32_t can store very large number values.

Counts of rotation produced by the encoder may seem confusing - how does this map to a rotation or distance travelled? The official documentation for the encoders tells us that one whole rotation of the wheel produces 358.3 encoder counts. We can therefore work out either how much rotation occurs for 1 encoder count ( degrees: \(\frac{360}{358.3}\), or radians: \(\frac{2\pi}{358.3}\)), or how much distance would be travelled by the wheel for one encoder count (wheel circumference divided by CPR, \(\frac{2 \pi r}{358.3}\)).

However, our robot moves itself with two wheels, and their combined interactions determine the resultant motion of the whole robot. Therefore, capturing the distance travelled by a single wheel is only the initial step in the process of modelling the motion. If one wheel rotates and the other does not, the robot will pivot (turn about) on the wheel that is not rotating. If both wheels rotate forwards at the same speed, the robot should move forwards. If both wheels rotate in opposite directions with the same speed, the robot should rotate on the spot. Therefore, it is necessary to also model the essential physical geometry of the robot, and to combine this with the independent rotation counts for the left and right wheels.

Odometry is the name given to this process of estimating overall motion from input measurements such as these. Developing and improving the odometry is your main task in this complete set of exercises. When we discuss the physical geometry of the robot and the mathematical operations of the model, we may use the phrase kinematics. In this first exercise, your task is to familiarise yourself with the code provided, verify that the example works, and make your first assessment of the accuracy and precision of the odometry by reporting odometry outputs.

Wheel radius and distance calibration

Approx. 3–5 hours

Open in Google Colab

Goal: use the supplied printed measurement sheet to estimate an effective shared wheel radius, apply it to the supplied Euler model, and test whether it improves distance estimates on measurements excluded from calibration.

The investigation and development of the kinematic model should begin with the wheel radius. In this exercise, we will start with the assumption that both wheels will have the same radius to simplify matters. Later exercises will guide you to explore for differences between the left and right wheels.

Starting simple will You can review OdometryModel.h to become familiar with the mathematical steps of the kinematic update as they are described in code. The two components of the update are translation (moving the robot position forwards or backwards linearly) and rotation.

The translation component, \(\Delta s\), a linear change in position, is calculated with the equation:

\[\Delta s=\frac{s_L+s_R}{2}\]

where \(s_L\) is the signed distance travelled by the left wheel and \(s_R\) is the signed distance travelled by the right wheel. In this simple model implementation, the change in the robot's centre position during one time step is calculated from the mean of \(s_L\) and \(s_R\). Recall that the model determines the distance a wheel travels by calculating the difference in encoder counts, \(\Delta n\), for a given time step:

\[s=\frac{2\pi r}{N}\Delta n\]

Here \(r\) is the wheel radius assumed by the model and \(N\) is the specified number of encoder counts per wheel revolution: 358.3. We can interpret the equation as calculating the distance travelled around the wheel circumference for one encoder count, then multiplying that value by the signed change in counts. This means that, the models estimate of displacement is dependent on the wheel radius parameter \(r\).

Rotation is calculated with the equation:

\[\Delta\theta=\frac{s_R-s_L}{B}\]

In this equation, \(B\) is introduced as the physical distance between the two wheels and is the subject of investigation in the next exercise. The numerator and denominator are both lengths, so their ratio gives an angle in radians. The amount the robot turns depends on the difference in wheel travel relative to the distance between the wheels.

We are interested in investigating both \(r\) and \(B\), and we have a choice about which to investigate first. In the translation equation, \(B\) is not involved. We can therefore investigate a shared wheel radius first, provided that the robot travels approximately straight. Once a useful estimate of \(r\) is found, rotation can be investigated with \(B\) in relative isolation, depending on our confidence in \(r\).

Translation: A Test Procedure

To calibrate the value \(r\), we will need to make external measurements of the robot and carefully place the robot at the beginning of each test. This is therefore an experimental procedure. When reporting an experiment, it is important to declare and discuss limitations in the overall approach. Human placement and reading introduce measurement uncertainty, while a repeatable viewing or alignment method can still introduce systematic bias.

To calibrate the wheel radius, we require the wheels to rotate while the robot moves a measured physical distance, and then compare that distance with the value calculated by the odometry model. Keeping the encoder CPR fixed, a repeatable discrepancy in distance can indicate that the radius is misrepresented in the odometry model. However, other variables influence this relationship, including whether the robot starts and stops precisely, whether both wheels maintain consistent contact with the surface, and whether either wheel slips. For example, placing the robot may cause a small wheel rotation.

In these tests, we must use the real physical distance travelled by the robot as a measured reference. That means we cannot flip the robot over and remove the wheels from the surface in an attempt to control the experimental variables: the wheel-surface interaction is part of the system being calibrated.

To move the robot a measured distance across a surface, we have a couple of potential approaches. One approach is to place the robot on the surface and then, without any motor activation, move the robot forwards by a known fixed distance as precisely as we can manage. A second approach is to command the robot to move itself by activating the motors. However, this second approach is not as simple as it seems.

Ordinary motor PWM commands do not use feedback to regulate wheel speed or position. This affects how consistently the robot can start, stop, and move. It is possible to activate the motors at a fixed power level for a period of time and then measure the physical distance travelled. However, differences in left and right motor performance are likely to produce a path that is not consistently straight.

To help you explore these properties, the Robot.h file contains helper functions:

robot.startMoveDistance(distance_mm)
robot.getMotionStatus()
robot.isMotionHelperRunning()

These functions can request a forward movement for a specified nominal distance. The helper initially converts that request into encoder-count targets using transparent nominal wheel geometry and applies a fixed PWM magnitude to each unfinished wheel. It monitors the two encoder targets independently, but it does not synchronise the wheel speeds, slow the robot as it approaches the target, or measure the physical distance travelled. It will therefore be necessary to measure how far the robot actually moved in every test. This physical measurement is the external reference against which you will compare the distance reported by your StampC3 local odometry model.

If you find that the motion helper is either too complicated or not reliable enough, you can choose to move the robot across a known distance by hand. In this approach, you should carefully consider how you can place, move, and stop the robot with the best consistency. The paper test map you have been provided contains markings intended to act as an external distance reference. However, you should check that it has been printed to scale.

For this first calibration, begin with the robot aligned with the printed \(+x\) direction and use the change in the local odometry's reported \(x\) position:

\[d_{\mathrm{est}}=\Delta x_{\mathrm{odom}}=x_{\mathrm{final}}-x_{\mathrm{initial}}\]

This comparison assumes that the robot moved approximately straight. Note that, the reported \(x\) is displacement along one axis, not the total distance travelled along a curved path. For example, if your robot does not move in a straight line, some of the motion contribution will be lost in the x axis and appear in the y axis. Therefore, you should also record any corresponding changes in \(y\) and \(\theta\). If a trial has appreciable sideways movement or heading change, it would be better to repeat it, rather than allowing its curvature to become part of the radius correction.

Let \(d_{\mathrm{actual}}\) be the signed physical displacement measured along the same printed \(x\)-axis. Because the odometry distance for the same movement is proportional to the radius used by the model, we can produce a correction with:

\[r_{\mathrm{new}}=r_{\mathrm{old}}\frac{d_{\mathrm{actual}}}{d_{\mathrm{est}}}\]

where:

  • \(d_{\mathrm{actual}}\) is the signed physical displacement measured along the printed \(x\)-axis;
  • \(d_{\mathrm{est}}\) is the signed change in \(x\) reported by the local odometry;
  • \(r_{\mathrm{old}}\) is the shared radius used in the odometry model during the test; and
  • \(r_{\mathrm{new}}\) is the effective shared-radius estimate produced by this test.

For example, suppose the odometry currently assumes:

\[r_{\mathrm{old}}=16.0\,\mathrm{mm}\]

You move the robot forwards by a measured distance:

\[d_{\mathrm{actual}}=300\,\mathrm{mm}\]

but the local odometry reports:

\[d_{\mathrm{est}}=285\,\mathrm{mm}\]

Then:

\[r_{\mathrm{new}}=16.0\frac{300}{285}=16.84\,\mathrm{mm}\]

The model underestimated the distance, so its wheel radius was too small and needs to increase. This result is an effective radius under the tested conditions, not necessarily the unloaded geometric radius of the wheel. Repeated trials and a measurement excluded from calibration are needed to establish whether the correction is useful beyond this example.

Wheel separation and heading calibration

Approx. 2–4 hours

Open in Google Colab

Goal: estimate effective wheel separation from observed turns, update the supplied model, and test heading estimates in both directions.

Exercise 2 established an effective wheel radius (assumed common to both left and right wheels) by comparing the local odometry's reported \(x\) displacement with independently measured physical displacement. We can now investigate the second geometric quantity in the supplied kinematic model: the distance between the two wheel contact points, represented by \(B\).

When the wheels travel equal distances in the same direction (same sign), the differential-drive model predicts no heading change: the robot moves straight forwards or straight backwards. When the wheels travel equal distances in opposite directions, the model predicts rotation on the spot about the midpoint between the wheels. Other combinations of left and right wheel travel produce a change in both position and heading, describing curved motion.

A simple thought experiment is to consider the ideal rolling case in which one wheel does not rotate, one wheel does rotate, and neither wheel slips. The stationary wheel contact point acts as a pivot for the robot body. The moving wheel follows an arc whose length is the distance travelled by that wheel, while the radius of the arc is the distance between the two wheel contact paths: the wheel separation, \(B\).

For a fixed distance travelled by the moving wheel, increasing the physical wheel separation does not change the arc length. Instead, that arc represents a smaller fraction of a circle of radius \(B\), so the robot turns through a smaller angle. With a smaller separation, the same arc length represents a larger fraction of the circle and produces a larger turn. During calibration we do not change the physical robot; we adjust the value of \(B\) assumed by the model so that its heading estimates better match physical observations.

Using the calibrated shared wheel radius stated in Exercise 2, the model calculates a signed distance for left right wheels, \(s_L\) and \(s_R\) repsectively, and then calculates the change in heading:

\[\Delta\theta=\frac{s_R-s_L}{B}\]

Here \(s_L\) and \(s_R\) are the signed wheel distances and \(B\) is the wheel separation assumed by the model. The numerator is the difference in wheel travel that produces the turn. Because the numerator and denominator are both lengths, their ratio gives an angle in radians. For the same observed wheel-distance difference, increasing the assumed \(B\) reduces the estimated turn, while decreasing it increases the estimated turn.

In OdometryModel.h, the public parameter wheelSeparationMm is used as \(B\). The resulting heading is accumulated in controller.odometry.pose.theta.

A Test Procedure

To calibrate \(B\), we need the robot to perform a measurable turn while we record both its local odometry heading and an external physical heading. An approximately in-place rotation is simplest and most convenient, where each wheel should rotate the same distance but with opposite sign. Similar to exercise 2, it will be useful to record x and y values reported by odometry to help you assess whether the rotation was controlled enough.

The Robot.h file provides the same style of motion-helper interface used in Exercise 2:

Call robot.startRotateAngle(...) once at the start of each trial, then continue acquiring measurements while polling the motion status. The requested angle and a COMPLETE status describe the helper request and its stopping condition; they are not measurements of the physical angle achieved. Measure the actual start and final headings from the printed sheet for every trial. Similar to exercise 2, you may also decide that you achieve better control and consistency by moving the robot by hand.

For this calibration, compare the physical heading change with the change reported by the local odometry. You can pick a quantity of rotation as a reference, 90 degrees may be a convenient starting value. Because estimated heading is inversely proportional to the separation used by the model, we can correct the separation with:

\[B_{\mathrm{new}}=B_{\mathrm{old}}\frac{\Delta\theta_{\mathrm{est}}}{\Delta\theta_{\mathrm{actual}}}\]

where:

  • \(\Delta\theta_{\mathrm{actual}}\) is the signed physical heading change measured from the printed reference;
  • \(\Delta\theta_{\mathrm{est}}\) is the signed heading change reported by the local odometry;
  • \(B_{\mathrm{old}}\) is the separation used in the odometry model during the test; and
  • \(B_{\mathrm{new}}\) is the effective separation estimate produced by this test.

For example, suppose the odometry uses \(B_{\mathrm{old}}=90\,\mathrm{mm}\). The physical robot turns through \(1.00\,\mathrm{rad}\), but the local odometry reports \(0.90\,\mathrm{rad}\). Then:

\[B_{\mathrm{new}}=90\frac{0.90}{1.00}=81\,\mathrm{mm}\]

The model underestimated the turn, so its separation was too large and needs to decrease. Positive and negative turns should both produce a positive value of \(B\) when the physical and odometry heading conventions agree. Very small turns make the calculation sensitive to placement and reading uncertainty, so several clearly measurable turn sizes in both directions are more informative than one tiny rotation.

This result is an effective wheel separation, conditional on the shared radius from Exercise 2, the tested surface, wheel slip, the physical reference, and the stopping motion. It is not necessarily identical to a single chassis measurement made with a ruler. A changed separation also changes later \(x\) and \(y\) estimates because they use the accumulated heading. Repeated trials and a turn excluded from calibration are therefore needed to establish whether the revised value is useful.

Approx. 3–6 hours

Goal: use your discovered robot geometry (wheel radius and wheel separation) to configure the supplied motion helpers. Then, program the robot to move in repeatable squares to evaluate the final reported odometry prediction against independently measured start and end poses.

A square offers a simple expectation: after four straight sides and four ninety degree turns, the robot should finish where it started, including it's heading. For example, we position the robot in the environment, and the robot initialises it's odometry model to \(x=0, y=0, \theta=0\). The robot then drives in the commanded square. Finishing, the robot reports \(x=0, y=0, \theta=0\), estimating that it has stopped where it started. However, we measure the final robot position as \(x=12.5, y=-22.1, theta=0.08\) - clearly, the odometry model has accrued error.

In the previous exercises we used relatively simple and short movments to calibrate the robot geometry. However, by tasking the robot to move in a more complex pattern, such as a square, any errors are compounded. Each individual movement may appear reasonable while a small distance or heading error is carried into every movement that follows. By the final side, an early heading error can contribute to both the final position and the final orientation. The square therefore tests the calibrated parameters together under a more demanding movement than the straight-line and on-the-spot trials used to estimate them.

This exercise is inspired by the University of Michigan Benchmark (UMBmark) for differential-drive robots. The original method uses repeated clockwise and anticlockwise square paths because two systematic effects can partly cancel in one direction but reinforce in the other. In this exercise, we will adopt a similar premise but alter aspects from the original source publication. For example, the square size, the use of motion helpers and measurement method differ from the original procedure. Therefore, this exercise is not a reproduction of the full published benchmark.

Importantly, during this benchmark the robot should not be configured to follow a line on the surface, such as the rectangle marked on the test sheet provided to you. Instead, the robot should attempt to move around the square using only the information available from its wheel encoders, without reference to external features. We are interested in observing the physical displacement that accumulates when the robot relies on encoder information to control its motion. If the robot were to follow the marked line, this would provide an external reference that could continually correct its trajectory and therefore mask the odometry errors that the benchmark is intended to reveal.

When running these tests, we expect that the final end position for each trial will vary. However, identifying the causes for each variation is not simple. Wheel slip, motor activation times, a shifted starting pose, surface variation, stopping behaviour and measurement error can produce patterns resembling geometry error. Repeated final end positions can reveal useful structure. A consistent offset between the clockwise and anticlockwise groups suggests a direction-dependent effect, while the spread within a group shows how repeatable the complete experiment was under the controlled conditions.

For each trial, first calculate the robot's physical closure from the independently measured start and end poses. We will represent these measurements with the subscript \(\mathrm{phys}\):

\[c_x=x_{\mathrm{phys,final}}-x_{\mathrm{phys,initial}},\qquad c_y=y_{\mathrm{phys,final}}-y_{\mathrm{phys,initial}},\qquad c_\theta=\operatorname{wrap}(\theta_{\mathrm{phys,final}}-\theta_{\mathrm{phys,initial}})\]

The quantities \(c_x\), \(c_y\), and \(c_\theta\) therefore describe the physically observed change in pose. They are not values reported by odometry. If the measured final pose exactly matched the measured initial pose, all three closure values would be zero.

Next, calculate the corresponding change reported by the local odometry. We will use the subscript \(\mathrm{odom}\) to distinguish these model estimates from the physical measurements:

\[\Delta x_{\mathrm{odom}}=x_{\mathrm{odom,final}}-x_{\mathrm{odom,initial}},\qquad \Delta y_{\mathrm{odom}}=y_{\mathrm{odom,final}}-y_{\mathrm{odom,initial}},\qquad \Delta\theta_{\mathrm{odom}}=\operatorname{wrap}(\theta_{\mathrm{odom,final}}-\theta_{\mathrm{odom,initial}})\]

Finally, define each endpoint residual as the independently measured physical closure minus the change estimated by odometry:

\[e_x=c_x-\Delta x_{\mathrm{odom}},\qquad e_y=c_y-\Delta y_{\mathrm{odom}},\qquad e_\theta=\operatorname{wrap}(c_\theta-\Delta\theta_{\mathrm{odom}})\]

For example, an ideal square would have zero physical closure, but do not replace your measured closure with zero: use the physical start and end poses you actually observed. The wrap operation maps an angular difference into one chosen interval, such as \((-\pi,\pi]\) radians or \((-180,180]\) degrees. Use the same convention and angular units throughout. Report position and heading residuals separately rather than combining millimetres and degrees into one unexplained score.

A square of side length \(L\) can be requested as four repetitions of a translation followed by a quarter-turn, \(\pi / 2\), with \(q\) determining the direction of the rotation:

\[\text{repeat four times:}\qquad \operatorname{move}(L),\quad \operatorname{rotate}(q\pi/2), \qquad q=+1\ \text{anticlockwise},\quad q=-1\ \text{clockwise}\]

Gyroscope bias and heading drift

Approx. 3–6 hours

Open in Google Colab

Goal: measure the gyroscope's stationary bias, examine how it affects integrated heading, and compare gyro and encoder estimates against the same physical reference.

In Exercise 3, the robot's change in heading was estimated from the difference between the distances travelled by its wheels. This estimate depends on the wheel geometry and on the assumption that rotation at the wheels represents rotation of the robot body. A gyroscope offers a different observation: it responds directly to rotation of the body about one of its sensor axes. Wheel slip may therefore affect the two estimates differently, although neither estimate is an independent measurement of the robot's physical heading.

A gyroscope reports angular velocity, or rate of rotation, rather than angle. A reading of \(30\) degrees/s means that the heading would change by approximately \(30\) degrees if that rate continued for one second. To estimate a complete turn, successive rate measurements must be accumulated over their measured time intervals. This process is called integration.

Ideally, a stationary gyroscope would report zero degrees/s. In practice, its readings may be scattered around a small non-zero mean. The mean stationary rate is a candidate zero-rate bias, while the sample-to-sample variation describes the short-term spread around it. These effects should not be confused: bias is a systematic offset in angular velocity, whereas heading drift is the accumulated change in the integrated angle. For example, a constant rate bias of \(0.2\) degrees/s would contribute \(4\) degrees of heading error after \(20\) seconds, even though the individual rate readings appear close to zero.

In the left panel, the horizontal calibration mean is the candidate bias estimated while the robot is stationary. The individual readings lie above and below this line because the measured rate also contains short-term variation and may change slowly with time. These components have different consequences when they are integrated. A positive bias adds a small positive angle during every sample interval, so its error grows steadily in one direction. Variation around the mean adds less regular positive and negative increments, but those increments are still accumulated rather than forgotten.

The right panel makes this accumulation visible. The uncorrected heading moves progressively away from the stationary reference because the rate retains a positive offset. Removing the fixed calibration mean makes the curve less steep, but it does not make it perfectly flat: a single constant correction cannot remove measurement variation or a bias that changes after calibration. The remaining drift is therefore useful evidence about the limits of the correction, rather than simply a failed result.

It is important to estimate and evaluate the correction using different data. For example, imagine we collected a dataset of samples with the sensor stationary and determined the mean to repesent bias. If we now used that bias value applied to the same dataset would make their corrected values sum to zero. However, in reality the operating circumstances of the sensor will change. These sensors are typically sensitive to aspects such as temperature variations and other environmental factors.

In the right panel of Figure 4, the example plot is intended to communicate that once a bias has been determined from a sampled dataset, it's subsequent application on later readings will likely not operate perfectly. We can observe that the fixed bias removed plot still gently trends upwards. A reduction in drift on this unseen data is useful evidence that the correction transfers under similar conditions, but any remaining residual drift shows how far that transfer is from perfect.

As such, a stationary mean is an operational estimate, not a permanent or exact property of the sensor. It may depend on warm-up time, temperature, how the robot is supported, and other conditions. Repeated stationary trials allow you to compare the variation within one record with changes between records. Before conducting and evaluating the turning trials, estimate the gyroscope bias from separate stationary calibration data and then keep it fixed. Do not adjust the bias for individual turns after comparing their estimated and externally measured final headings, because this would tune the correction to the result it is intended to predict.

For a simple left-endpoint integration, use the previous corrected rate over the measured sample interval:

\[\hat{\theta}_{k+1}=\hat{\theta}_k+(\omega_k-\hat b)\Delta t_k,\qquad \Delta t_k=(t_{k+1}-t_k)\times10^{-6}\]

Here \(t_k\) is the IMU timestamp in microseconds. Therefore, \(\Delta t_{k}\) is the difference in time between the measurement samples (sensor reading) taken. \(\omega_k\) is the measured rate (sensor reading) in degrees/s, \(\hat b\) is the fixed bias estimate in degrees/s, and the resulting \(\hat{\theta}\) is in degrees. For example, a corrected rate of \(20\) degrees/s applied for \(0.01\) seconds adds \(0.2\) degrees to the heading estimate. Checking one such calculation by hand is a useful way to find a missing \(10^{-6}\) conversion or a mixture of degrees and radians.

The StampC3_Template code has a class provided to you to operate the gyro sensor. The class RobotIMU_c has the helper function gyroscopeToDegreesPerSecond(...) which you can use to convert a gyro reading into degrees. The local encoder odometry stores heading in radians, so one estimate must be converted before the two are compared. Their timestamps also have different meanings: timestamp_us is recorded after the IMU read, while the controller's millisecond time (the argument provided, unsigned long now) describes the surrounding acquisition cycle. When recording data, it would be best to keep both time values rather than presenting the measurements as exactly simultaneous.

The RobotIMU_c class configures the IMU sensor to sample at \(104\) Hz, close to the controller's \(100\) Hz update rate. The class does not choose an axis, all three are available to you. The class does not estimate bias or integrate heading for you.

In this exercise you will first establish which sensor axis and sign correspond to physical yaw. You will then estimate bias from stationary evidence and test it on data that was not used for the estimate. Finally, you will compare gyro and encoder heading changes with the same external start and final headings. Agreement between the onboard estimates is useful, but the external observation is needed to assess whether either one describes the physical turn.
