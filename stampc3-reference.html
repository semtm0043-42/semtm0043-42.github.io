02
Hardware-facing capabilities

StampC3 and extension-board interface

The supplied code uses the StampC3 as an external master for the Pololu robot. It starts I2C at 400 kHz, reads the StampC3 button on pin 3, drives its on-board RGB LED through setLED(...), starts serial at 115200 baud, and can create a WiFi access point for TCP telemetry. It also uses the shared I2C bus to acquire inertial measurements directly from the LSM6DS33 and, when available, the LIS3MDL; those measurements do not pass through the opaque middleware.

What the template does and does not specify

  • I2C: the robot interface is addressed as 0x08; requests and data layouts are defined in i2c_datatypes.h.
  • Serial: the sketch initialises Serial at 115200 baud. Whether a particular program prints a record depends on its own code.
  • WiFi/TCP: RobotWifiAP_c owns the access point and one TCP connection. TCP telemetry is delivered only while a client is connected; the supplied controller independently attempts Serial telemetry every 50 ms when Serial is available.
  • IMU: RobotIMU_c provides raw, timestamped sensor readings and range-specific unit conversions. It requires the Pololu LSM6 and LIS3MDL Arduino libraries and does not remove bias, filter readings, integrate motion, or calculate orientation.
  • Extension hardware: only interfaces represented in the supplied code should be assumed available without checking the hardware documentation.

Robot_c · cached state

04
Robot_c · full public API

Request, command, and inspect

Named left/right getters follow the shared convention: channel 0 is left and channel 1 is right for both motor commands and encoder counts.

Every method below which performs an I2C transaction returns a Boolean success value. Read caches change only after a complete response of the expected size; write caches change only after the register and payload are both acknowledged. Command success confirms delivery, not physical completion.

05
Motion helpers · controlled apparatus

Nominal distance and rotation motions

The helpers provide limited, asynchronous motions for repeatable odometry experiments. They use a fixed internal PWM and direct encoder feedback. They start with nominal geometry: 16.5 mm left and right wheel radii and 86.18 mm wheel separation. They are relative to the encoder position at the moment of the request: startRotateAngle(PI / 2.0f) requests a nominal left turn from the current orientation, not an absolute heading.

They intentionally bypass the ordinary motor-command path. They are therefore not suitable for characterising motor deadband, gain, non-linearity, lag, or speed response. Completion only means both configured encoder targets were reached; it does not establish that the physical distance or angle was exact. Measure the outcome independently.

After calibrating odometry, setMotionHelperGeometry(...) can apply the frozen left radius, right radius, and wheel separation to subsequent helper requests. Encoder resolution remains fixed at 358.3 counts per revolution. This setting affects only conversion of requested helper motions into encoder targets; it does not alter the middleware pose estimate. Power-up, reset, or a new team-name configuration restores the nominal helper geometry.

FieldMeaning
stateMOTION_STATUS_IDLE, RUNNING, COMPLETE, TIMEOUT, or CANCELLED. Both distance and rotation requests use the same completion state.
modeMOTION_MODE_DISTANCE or MOTION_MODE_ROTATION; use this field to identify the type of the most recent helper request.
elapsed_msElapsed helper time in milliseconds.

Ownership and observation rules

  • A later setMotorPWM(...) command cancels a running helper and takes ownership of the motors.
  • A later helper command replaces the preceding helper request.
  • Encoder, surface-sensor, pose, and helper-status requests may be made while a helper runs; they do not interrupt it. Record encoder snapshots explicitly with getEncoders() around the helper request.
  • The helper stops at a safety timeout if its encoder targets are not reached.

I2C protocol · packed types

Messages, types, and channel order

07
Timing · non-blocking polling

TaskTimer_c

TaskTimer_c helps a sketch run a task at a loose interval without using delay(). It is not a background task, interrupt, or real-time scheduler: your code still calls isReady(...) regularly and chooses what to do when it returns true.

SignaturePurpose
TaskTimer_c(unsigned long interval_ms = 0)Creates a timer. An interval of zero is ready every time it is checked.
setIntervalMS(unsigned long interval_ms)Changes the interval for later checks.
isReady(unsigned long now_ms)Returns true when the interval has elapsed since the last reset. It does not reset the timer.
resetTimer(unsigned long now_ms)Starts the next interval from the supplied time.
isReady()
resetTimer()		Convenience overloads that use the StampC3 millis() clock.

Typical pattern 

TaskTimer_c log_timer(100);

void loop() {
  unsigned long now = robot.getMillis();

  if (log_timer.isReady(now)) {
    log_timer.resetTimer(now);
    recordOneMeasurement();
  }

  runOtherWork();
}

Resetting when the check is accepted starts the next interval from that supplied timestamp. The timer stores only one timestamp and does not queue missed calls, so slow or delayed work can postpone the next opportunity but does not create a burst of catch-up calls. The supplied controller uses this pattern for its 10 ms update and 50 ms telemetry timers.

08
Local estimation · direct inertial sensing

OdometryModel_c and RobotIMU_c

The template exposes two routes that are deliberately separate from the pose supplied through Robot_c. controller.odometry.pose is a student-editable estimate calculated locally on the StampC3 from encoder changes. RobotIMU_c acquires raw inertial measurements directly from the sensor ICs. Neither route is an independent observation of the robot's physical position or heading: compare estimates against an external physical reference when evaluating them.

Keep the names distinct when reading or plotting data. robot.pose is the latest middleware-provided pose snapshot, whereas the supplied controller's CSV x, y, and theta fields come from controller.odometry.pose.

09
Controller and transport APIs

Controller_c and RobotWifiAP_c

Controller_c is the supplied nominal line follower. RobotWifiAP_c is a one-client TCP transport helper. Their separation is deliberate: controller logic creates a telemetry record; the network class only delivers bytes.

On each accepted 10 ms controller cycle, the controller attempts to refresh surface, encoder, and middleware-pose caches. The local odometry model advances only after a successful encoder request. Every 50 ms it attempts to send the same 14-field CSV record over TCP and, independently, over Serial: timestamp, local odometry x/y/theta, requested left/right PWM, left/right encoder counts, DN1–DN5 readings, and controller signal.

The header also currently exposes an integer named rotation_count, but the supplied implementation neither initialises nor uses it. Do not treat it as a measurement or supported controller result.
